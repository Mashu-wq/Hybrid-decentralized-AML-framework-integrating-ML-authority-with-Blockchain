1. EXECUTIVE SUMMARY
================================================================================

This system is a production-grade, cloud-native Anti-Money Laundering (AML)
platform that combines two core innovations:

  1. HYPERLEDGER FABRIC BLOCKCHAIN — provides tamper-proof, multi-organization
     audit trails for KYC records, fraud alerts, and transaction receipts that
     regulators can verify independently without trusting the bank.

  2. MACHINE LEARNING ENSEMBLE — six fraud detection models (Random Forest,
     XGBoost, LightGBM, GraphSAGE GNN, Autoencoder, Ensemble) trained on the
     Elliptic Bitcoin Transaction Dataset, with SHAP/LIME/Counterfactual
     explainability, produce fraud probability scores on every transaction.

The platform is built as 10 independent microservices written in Go (backend)
and Python (ML), communicating via gRPC, Kafka, and REST. The architecture
follows domain-driven design with strict dependency inversion — every service
defines port interfaces, and implementations are injected at startup.

Dataset: Elliptic Bitcoin Transaction Dataset
  203,769 transactions | 166 features | 46,564 labeled (9.7% illicit)
  Temporal 80/20 split | SMOTE oversampling | Benchmark: LightGBM ROC-AUC 96.49%

4.1  API GATEWAY
------------------------------------------------------------------------
  Location  : services/api-gateway/
  Runtime   : Traefik (config-driven, no custom Go binary for routing)

  Language  : Go (custom middleware only)

  RESPONSIBILITIES:

    /auth/*          → IAM Service     (gRPC :50060)

4.2  IAM SERVICE  (Identity & Access Management)
------------------------------------------------------------------------
  Location  : services/iam-service/
  Port      : gRPC :50060
  Language  : Go
  Database  : PostgreSQL (users, roles, permissions, refresh tokens,
                          audit events)
  Cache     : Redis (JWT blacklist, rate limiting, MFA challenges)

  RESPONSIBILITIES:
    - User registration with role assignment
    - JWT-based authentication (access tokens + refresh tokens)
    - Multi-Factor Authentication (TOTP + backup codes)
    - Role-Based Access Control (RBAC)
    - Token rotation and revocation
    - Account lockout after failed attempts

  KEY COMPONENTS:

    AuthService (auth_service.go):
      - Register(email, password, role) — bcrypt cost 12 password hashing
      - Login(email, password, mfaCode) — rate-limited, MFA-aware
      - VerifyMFA(challengeID, code) — TOTP or backup code verification
      - RefreshTokens(refreshToken) — token rotation with device binding
      - Logout(jti, logoutAll) — JTI blacklisting in Redis
      - ChangePassword — verifies current password before update
      - ValidateToken — used by API Gateway on every request

    TokenService (token_service.go):
      - Access tokens  : JWT, 15-minute TTL, signed with JWT_SECRET
      - Refresh tokens : random 256-bit, SHA-256 hashed in PostgreSQL,
                         7-day TTL, device-bound
      - Revocation     : JTI stored in Redis until token expiry

    MFAService (mfa_service.go):
      - TOTP secret generation (RFC 6238)
      - QR code URL generation for authenticator apps
      - 8 backup codes per user (bcrypt hashed in PostgreSQL)
      - Backup code consumption (one-time use, removed after use)

  SECURITY FEATURES:
    - No user enumeration: unknown email returns same error as wrong password
    - Rate limiter: 5 failed attempts in 15 min → account locked 15 min
    - Device binding: refresh token tied to deviceID, mismatch triggers
      immediate revocation and audit log
    - Password policy: min 12 chars, uppercase + lowercase + digit + special

  ROLES:
    ADMIN    — full system access, user management
    ANALYST  — read fraud alerts, update alert status
    AUDITOR  — read-only access to audit trails and reports
    VIEWER   — dashboard access only

4.3  KYC SERVICE  (Know Your Customer)
------------------------------------------------------------------------
  Location  : services/kyc-service/
  Port      : gRPC :50061
  Language  : Go
  Database  : PostgreSQL (customers, encrypted PII, documents, audit)
  External  : Encryption Service (gRPC :50067) for PII encryption
              Blockchain Service (HTTP :9005) for ledger writes
              ML Service (gRPC :50051) for face verification
              Kafka for KYC event publishing

  RESPONSIBILITIES:
    - Customer onboarding and KYC registration
    - PII encryption/decryption via Vault transit
    - Identity hash generation: SHA-256(name+dob+docType+docNumber+country)
    - Document management (passport, national ID, utility bill)
    - KYC status lifecycle management
    - Blockchain write: RegisterCustomer and UpdateKYCStatus on kyc-channel

  KYC STATUS LIFECYCLE:
    PENDING → APPROVED (compliance officer approves)
    PENDING → REJECTED (documents invalid)
    APPROVED → SUSPENDED (suspicious activity)
    APPROVED → REJECTED (fraud confirmed)
    SUSPENDED → APPROVED (cleared after review)
    SUSPENDED → REJECTED (confirmed fraud)
    REJECTED → PENDING (re-application allowed)

  RISK LEVELS:
    UNSPECIFIED → LOW → MEDIUM → HIGH → CRITICAL

  PII ENCRYPTION FLOW:
    1. KYC Service receives customer name, DOB, passport number
    2. Calls Encryption Service: BatchEncryptPII()
    3. AES-256-GCM ciphertext stored in PostgreSQL
    4. Only SHA-256(document) written to blockchain
    5. Plaintext PII never touches the blockchain or logs

  KEY DATA:
    Customer record: customerID, identityHash, kycStatus, riskLevel,
                     countryCode, verifierID, blockchainTxID, timestamps
    EncryptedPII   : encrypted name, DOB, nationality, document fields
    Documents      : docType, s3Key, ocrData, verificationStatus

4.4  TRANSACTION SERVICE
------------------------------------------------------------------------
  Location  : services/transaction-service/
  Port      : gRPC :50062
  Language  : Go
  Database  : MongoDB (time-series enriched transactions)
  Cache     : Redis (velocity sorted sets, risk score TTL 5 min,
                      last_tx per customer)
  Messaging : Kafka consumer (transactions.raw)
              Kafka producer (alerts.created)
  External  : ML Service (gRPC :50051) for fraud prediction
              Blockchain Service (HTTP :9005) for audit receipt

  RESPONSIBILITIES:
    - Consume raw transactions from Kafka (transactions.raw topic)
    - Feature extraction (6 categories, Redis-backed)
    - ML fraud prediction via gRPC PredictFraud RPC
    - Alert threshold evaluation (FATF risk-based)
    - Velocity tracking and risk score caching in Redis
    - Persist enriched transaction to MongoDB
    - Fire-and-forget blockchain audit receipt
    - Synchronous ingest via gRPC IngestTransaction(sync=true)

  FULL PIPELINE (ProcessTransaction):
    Step 1 — Validate raw transaction input
    Step 2 — Feature extraction:
               Temporal : tx_hour, day_of_week, is_weekend,
                          time_since_last_tx, tx_frequency_1h/24h
               Amount   : amount_usd_equiv, avg_amount_7d/30d,
                          std_amount_30d, amount_deviation_score,
                          velocity_1h/24h
               Geographic: geographic_risk_score, cross_border_flag,
                           country_change_2h, distance_km_from_last
               Merchant : merchant_risk_score, is_high_risk_merchant
               KYC      : customer_risk_score, kyc_risk_level,
                          days_since_kyc, total_tx_count_30d
               Graph    : pagerank, clustering_coefficient,
                          betweenness_centrality, louvain_community_id,
                          hops_to_known_fraudster, direct_fraud_neighbors
    Step 3 — gRPC PredictFraud → ML Service
               Returns: fraudProbability, riskLevel, modelVersion,
                        predictionID, shapValues
               Fallback: heuristic score if ML unavailable
    Step 4 — Redis update:
               velocity sorted set (ZADD with timestamp)
               last_tx cache per customer
               risk score (SET with 5-min TTL)
    Step 5 — Alert routing:
               threshold = alertThresholds[kyc_risk_level]
               FATF risk-based thresholds:
                 HIGH/CRITICAL customer → lower threshold → higher recall
                 LOW customer → higher threshold → fewer false positives
               if fraudProb > threshold → publish to Kafka alerts.created
    Step 6 — MongoDB persist: enriched transaction document
    Step 7 — ASYNC blockchain anchor (goroutine, never blocks pipeline):
               POST /audit/transaction → Blockchain Service
               RecordTransactionProcessed on audit-channel

  KAFKA TOPICS:
    Consumed : transactions.raw  (inbound transactions from core banking)
    Produced : alerts.created    (fraud alerts for Alert Service)

  VELOCITY TRACKING (Redis sorted sets):
    Key pattern : velocity:{customerID}:{window}
    Windows     : 1h, 24h, 7d
    Data stored : (txHash, timestamp) pairs
    Metrics     : count, total USD, distinct countries, distinct merchants

4.5  ML SERVICE
------------------------------------------------------------------------
  Location  : services/ml-service/
  Port      : REST :8000 (FastAPI), gRPC :50051
  Language  : Python 3.11

  RESPONSIBILITIES:
    - Serve 6 fraud detection models (ensemble by default)
    - Real-time single transaction prediction (PredictFraud RPC)
    - Batch prediction (up to 1000 transactions per call)
    - Server-streaming predictions for real-time dashboard
    - SHAP explanations (TreeExplainer for trees, KernelExplainer fallback)
    - LIME local explanations per prediction
    - Counterfactual generation (minimum perturbation)
    - Model metrics and comparison API
    - A/B testing via PredictWithModel RPC
    - Model retraining trigger (MLflow run)
    - Face verification for KYC biometrics

  MODELS:
    Model          Class              Algorithm / Architecture
    -----------    ----------------   ---------------------------------
    Random Forest  RandomForestModel  500 trees, max_depth=12,
                                      class_weight=balanced
    XGBoost        XGBoostModel       500 estimators, scale_pos_weight=9,
                                      lr=0.05, Optuna HPO
    LightGBM       LightGBMModel      1000 leaves, is_unbalance=True,
                                      lr=0.05, Optuna HPO
    GNN            GNNFraudModel      3-layer GraphSAGE PyTorch Geometric
                                      85→256→128→64→2, dropout=0.3
    Autoencoder    AutoencoderModel   85→64→32→16→32→64→85 (PyTorch)
                                      inverted scoring (Elliptic-specific)
    Ensemble       EnsembleModel      Weighted average:
                                      LightGBM:0.35, RF:0.33, XGB:0.32

  FEATURE PIPELINE:
    Input : TransactionFeatures proto (85 selected Elliptic features)
    Path 1: If elliptic_features map populated → use directly
    Path 2: If structured fields provided →
              _structured_to_elliptic_array() maps 38 bank wire fields
              into Elliptic positions; 47 positions zero-padded

  BENCHMARK RESULTS (Elliptic, Colab, 2026-06-08):
    Model         Precision  Recall   F1      ROC-AUC  PR-AUC
    LightGBM      64.61%     68.18%   66.35%  96.49%   69.7%
    Random Forest 88.34%     56.92%   69.23%  96.38%   68.2%
    XGBoost       70.64%     63.24%   66.74%  95.97%   69.1%
    GNN           22.34%     66.45%   33.44%  88.86%   54.7%
    Autoencoder    6.61%     68.15%   12.05%  70.94%   38.9%

  EXPLAINABILITY:
    SHAP  : TreeExplainer for RF/XGB/LGB, KernelExplainer for GNN/AE
            Top-5 SHAP contributions returned per prediction
            Serialized to JSON, stored in PostgreSQL + blockchain
    LIME  : TabularExplainer, local linear model per prediction
            Accessed via GetLIMEExplanation RPC by prediction_id
    CF    : Counterfactual: minimum-perturbation to flip prediction
            Accessed via GetCounterfactual RPC by prediction_id

  REST ENDPOINTS (FastAPI, :8000):
    POST /predict        → single transaction prediction
    POST /predict/batch  → batch up to 1000 transactions
    POST /explain        → SHAP explanation for a prediction
    GET  /compare        → model comparison table
    GET  /docs           → Swagger UI

  gRPC SERVICE (FraudMLService, :50051):
    PredictFraud        — primary hot-path prediction
    BatchPredictFraud   — bulk reprocessing
    StreamPredictions   — server-side streaming for dashboard
    GetLIMEExplanation  — LIME explanation by prediction_id
    GetCounterfactual   — counterfactual by prediction_id
    GetModelMetrics     — live performance metrics
    GetModelComparison  — all-model comparison table
    PredictWithModel    — A/B test specific model
    TriggerRetraining   — ADMIN: kick off MLflow retraining
    VerifyFace          — KYC biometric face matching

4.6  ALERT SERVICE
------------------------------------------------------------------------
  Location  : services/alert-service/
  Port      : gRPC :50063
  Language  : Go
  Database  : PostgreSQL (alerts, SHAP values, notification log)
  Cache     : Redis (deduplication hashes, TTL-based)
  Messaging : Kafka consumer (alerts.created)
  External  : Blockchain Service (HTTP :9005) for alert anchoring
              WebSocket hub for real-time dashboard push

  RESPONSIBILITIES:
    - Consume fraud alerts from Kafka (alerts.created)
    - Deduplicate alerts: Redis hash (customerID + txHash + alertID)
    - Persist alert to PostgreSQL with SHAP values (JSONB column)
    - Write alert record to blockchain alert-channel
    - Push real-time WebSocket notification to compliance dashboard
    - Alert lifecycle management (status transitions)
    - Notification dispatch (email, Slack, webhook)
    - Alert escalation (auto-escalate unresolved alerts)

  ALERT STATUS MACHINE:
    OPEN → INVESTIGATING → RESOLVED (terminal)
    OPEN → ESCALATED     → RESOLVED (terminal)
    OPEN → FALSE_POSITIVE (terminal)
    INVESTIGATING → FALSE_POSITIVE (terminal)
    INVESTIGATING → ESCALATED

  DEDUPLICATION:
    Hash = SHA-256(customerID + txHash + alertID)
    Stored in Redis with TTL
    Prevents duplicate alerts from Kafka at-least-once delivery

  WEBSOCKET:
    Dashboard clients connect to ws://host:50063/ws
    Alert Service broadcasts WSMessage on every new alert
    Message payload: alertID, customerID, fraudProbability,
                     riskLevel, timestamp, topSHAPFeatures

  NOTIFICATION DISPATCHER:
    Channels: Email (SMTP), Slack (webhook), Generic webhook
    All notifications logged to PostgreSQL notification_log table
    Configurable per risk level (CRITICAL → email + Slack, LOW → none)

    - Anchor SHA-256(SAR PDF) on blockchain audit-channel

    1. Compliance officer triggers SAR generation via gRPC
    2. Case Service assembles transaction history, alert data, KYC info
    3. PDF generated with case summary, evidence, timeline
    4. PDF uploaded to S3 → returns s3Key
    5. SHA-256(PDF content) computed
    6. POST /audit/sar → Blockchain Service
       RecordSARFiled(caseID, sarHash, s3Key, filedAt, generatedBy)
    7. Blockchain record anchors the document permanently
    8. Regulators can verify PDF integrity: SHA-256(S3 download) vs on-chain hash

6. COMMUNICATION PATTERNS
================================================================================

  PATTERN 1 — Synchronous gRPC (internal service-to-service)
  -----------------------------------------------------------
    Used for: request-response operations where the caller needs the result
    Protocol: gRPC over HTTP/2, Protocol Buffers serialization
    TLS: TLS 1.3 enforced in production (mutual TLS optional)

    Calls:
      API Gateway     → IAM Service        (ValidateToken on every request)
      Transaction Svc → ML Service         (PredictFraud on every transaction)
      KYC Service     → Encryption Service (BatchEncryptPII, BatchDecryptPII)
      KYC Service     → ML Service         (VerifyFace for biometrics)
      Any Service     → Blockchain Svc     (HTTP REST, not gRPC)

  PATTERN 2 — Asynchronous Kafka (event-driven)
  ----------------------------------------------
    Used for: high-volume event processing where decoupling is needed
    Delivery: at-least-once (deduplication in Alert Service)

    Topics:
      transactions.raw  : Published by core banking / external systems
                          Consumed by Transaction Service
                          Payload: RawTransaction proto
      alerts.created    : Published by Transaction Service
                          Consumed by Alert Service
                          Payload: AlertEvent JSON

  PATTERN 3 — HTTP REST (blockchain service only)
  ------------------------------------------------
    The Blockchain Service exposes HTTP REST (not gRPC) because:
      - Chaincode invocations are already async within Fabric
      - HTTP is simpler for fire-and-forget calls from transaction pipeline
    All other inter-service calls use gRPC

  PATTERN 4 — WebSocket (real-time dashboard)
  --------------------------------------------
    Alert Service maintains a WebSocket hub
    Dashboard clients subscribe to ws://host:50063/ws
    New fraud alerts are pushed immediately without polling
    Each WSMessage contains: alertID, customerID, fraudProb, riskLevel,
                              topSHAPFeatures, timestamp

  PATTERN 5 — gRPC Server-Streaming (ML dashboard)
  --------------------------------------------------
    ML Service: StreamPredictions RPC
    Client receives a stream of PredictFraudResponse messages
    Filtered by min_fraud_prob threshold
    Used by real-time monitoring dashboard

================================================================================

  DATA SOURCE:
    Elliptic Bitcoin Transaction Dataset (Kaggle)
      elliptic_txs_features.csv  — 166 features, 203,769 rows
      elliptic_txs_classes.csv   — labels (1=illicit, 2=licit, unknown)
      elliptic_txs_edgelist.csv  — directed transaction graph edges

  PREPROCESSING (ml/data/preprocessor.py):
    1. Load features + class files, merge on txId
    2. Filter: keep only labeled rows (46,564 of 203,769)
    3. Remap: 1(illicit)→1(fraud), 2(licit)→0(legit)
    4. Temporal split: first 70% of time_steps→train, rest→test
       (avoids data leakage — preserves temporal order)
    5. SMOTE on training set only: minority/majority ratio 0.5
    6. Optional StandardScaler (skipped for tree models)

  FEATURE ENGINEERING (ml/features/engineering.py):
    Raw Elliptic: 166 features (txId, time_step, feature_1…feature_165)
    Selected    : 85 features (SELECTED_FEATURE_INDICES)
                  indices 1–68 (local transaction features)
                  indices 94–110 (aggregated neighborhood features)
    Selection basis: LightGBM feature importance ranking

    Production mapping (_structured_to_elliptic_array):
      38 positions → real bank wire transfer fields
                     (amount, velocity, geo risk, KYC risk, network, etc.)
      47 positions → zero-padded (Bitcoin-specific graph aggregates)
      This is the DOMAIN ADAPTATION layer for production inference

  MODEL TRAINING:
    Trainer    : ml/models/ (each model has fit(), predict_proba(), save(), load())
    Tracking   : MLflow (MLFLOW_TRACKING_URI in .env)
    Artifacts  : .pkl (scikit-learn), .pt (PyTorch models)
    HPO        : Optuna (XGBoost, LightGBM)

  EXPLAINABILITY (ml/explainability/):
    shap_explainer.py   :
      - TreeExplainer for RF, XGB, LGB (fast, exact)
      - KernelExplainer for GNN, Autoencoder (approximate)
      - Returns: feature name, SHAP value, base value
      - Serialized as JSON, stored in PostgreSQL + blockchain
    lime_explainer.py   :
      - TabularExplainer
      - Fits local linear model around one prediction
      - Returns: LIMEFeatureWeight list (feature, weight, condition)
    counterfactual.py   :
      - Minimum-perturbation counterfactual generation
      - Answers: "what would need to change to not be flagged?"
      - Returns: CounterfactualChange list (feature, current, suggested, delta)

  EVALUATION (ml/evaluation/evaluator.py):
    Metrics: Precision, Recall, F1, Accuracy, ROC-AUC, PR-AUC,
             TP, FP, TN, FN, avg latency ms, p95 latency ms
    Functions:
      evaluate_model(model, X_test, y_test) → EvalMetrics
      compare_models(models, X_test, y_test) → ModelComparisonReport
    COLAB_BENCHMARK: hardcoded actual results from 2026-06-08 training run

  GNN SPECIAL NOTES:
    Training : uses full Elliptic edge list (directed transaction graph)
    Inference: uses self-loop edge index (no message passing)
               → effectively an MLP in production
    Full graph inference: predict_proba_graph(X, edge_index)
               requires pre-built subgraph from PostgreSQL edge table

  AUTOENCODER SPECIAL NOTES:
    Training : on licit transactions only (learns normal behavior)
    Scoring  : reconstruction error as anomaly score
    inverted=True on Elliptic: fraud txns have LOWER reconstruction error
               because they have simpler, more uniform features
    Use case : novelty detection, not primary classification

8. BLOCKCHAIN LAYER (SUMMARY)
================================================================================

  Network      : Hyperledger Fabric v2.5, permissioned
  Organizations: 3 (Org1/PrimaryBank, Org2/Regulator, Org3/PartnerBank)
  Consensus    : Raft (3 orderers, 1 per org, CFT — tolerates 1 failure)
  Channels     : 3 (kyc-channel, alert-channel, audit-channel)
  Chaincodes   : 3 (kyc-contract, alert-contract, audit-contract)
  Endorsement  : MAJORITY (at least 2 of 3 orgs must sign every write)
  Commit time  : ~400–900ms (measured)
  PII on-chain : NONE — only SHA-256 hashes

  KEY CONTRACTS:
    kyc-contract   : RegisterCustomer, UpdateKYCStatus, GetKYCRecord,
                     GetKYCHistory, ListPendingKYC
    alert-contract : CreateAlert, UpdateAlertStatus, GetAlertsByCustomer,
                     GetAlertsByRiskLevel, GetAlertStats
    audit-contract : RecordTransactionProcessed, RecordModelPrediction,
                     RecordSARFiled, RecordInvestigatorAction,
                     GetAuditTrail, GetComplianceReport

9. TRANSACTION PROCESSING PIPELINE (END-TO-END)
================================================================================

  A wire transfer enters the system and is scored for fraud:

  [Core Banking System]
        |
        | → Kafka: transactions.raw
        |
  [Transaction Service — Kafka Consumer]
        |
        |→ Step 1: Validate RawTransaction
        |→ Step 2: Feature Extraction
        |          Redis: velocity_1h, velocity_24h, last_tx timestamp
        |          Redis: customer risk score (5-min TTL)
        |          Lookup: geographic_risk_score, merchant_risk_score
        |          Compute: amount_deviation_score, cross_border_flag
        |
        |→ Step 3: gRPC PredictFraud → [ML Service :50051]
        |          Feature vector (85-dim) serialized as TransactionFeatures
        |          ML Service: Ensemble(LGB, RF, XGB) → weighted average
        |          SHAP values computed for top-5 features
        |          Returns: fraudProbability, riskLevel, shapValues, predictionID
        |          Fallback: heuristic score if ML unavailable
        |
        |→ Step 4: Redis Update
        |          ZADD velocity:{customerID}:1h  → sorted set
        |          ZADD velocity:{customerID}:24h → sorted set
        |          SET  last_tx:{customerID}       → timestamp
        |          SET  risk_score:{customerID}    → TTL 5 min
        |
        |→ Step 5: Alert Decision
        |          threshold = alertThresholds[kyc_risk_level]
        |          HIGH/CRITICAL customer → lower threshold (FATF)
        |          if fraudProb > threshold:
        |            Kafka publish: alerts.created
        |            Payload: AlertEvent (alertID, customerID, txHash,
        |                      fraudProb, riskLevel, shapJSON, featuresJSON)
        |
        |→ Step 6: MongoDB Save
        |          EnrichedTransaction document:
        |          {raw, features, fraudProbability, riskLevel,
        |           modelVersion, shapValues, alertCreated, processedAt}
        |
        |→ Step 7: Blockchain (ASYNC goroutine — never blocks)
        |          POST /audit/transaction → [Blockchain Service :9005]
        |          RecordTransactionProcessed on audit-channel
        |          14 fields including txHash, fraudProbability, alertFired
        |          Fabric: MAJORITY endorsement → Raft ordering → committed
        |          All 3 org ledgers now hold the immutable receipt
        |
  [Alert Service — Kafka Consumer: alerts.created]
        |
        |→ Deduplicate via Redis SHA-256 hash
        |→ Persist to PostgreSQL (alert + SHAP JSONB)
        |→ POST /alerts → [Blockchain Service] → alert-channel
        |→ WebSocket broadcast to compliance dashboard
        |→ Notification dispatch (email/Slack if CRITICAL/HIGH)
        |
  [Case Service — if escalated]
        |→ Compliance officer creates case
        |→ SAR PDF generated → uploaded to S3
        |→ POST /audit/sar → audit-channel (SHA-256 hash anchored)
        |→ POST /audit/action → audit-channel (investigator actions)

10. SECURITY ARCHITECTURE
================================================================================

  CONTROL                    IMPLEMENTATION
  -------------------------  --------------------------------------------------
  Authentication             JWT (access 15 min) + refresh token (7 days)
                             Token rotation on every refresh
  Multi-Factor Auth          TOTP (RFC 6238) + 8 one-time backup codes
  Authorization              RBAC — role permissions checked per endpoint
  Rate limiting              100 req/min (public), 5 failed logins → lockout
  Account lockout            15 min lockout after 5 failed login attempts
  Password policy            Min 12 chars, upper+lower+digit+special
  PII encryption             AES-256-GCM via HashiCorp Vault transit engine
  Transport security         TLS 1.3 on all inter-service gRPC connections
  SQL injection              All queries parameterized (no string interpolation)
  Token revocation           JTI stored in Redis until token expiry
  Device binding             Refresh tokens bound to deviceID; mismatch revokes
  No user enumeration        Unknown email returns same error as wrong password
  Blockchain immutability    SHA-256 chained blocks, MAJORITY multi-org signing
  SAR integrity              SHA-256(PDF) anchored on-chain; S3 stores document
  PII on blockchain          Never stored — only SHA-256(document) on-chain
  Secret management          All secrets in .env (gitignored); Vault for PII keys
  Audit logging              All auth events written to PostgreSQL audit_events
                             All blockchain writes create immutable audit records

  OWASP TOP 10 COVERAGE:
    Broken Access Control   → RBAC on every endpoint, JWT validation at gateway
    Cryptographic Failures  → AES-256-GCM, bcrypt cost 12, TLS 1.3
    Injection               → Parameterized queries throughout
    Insecure Design         → Defense-in-depth, PII never on blockchain
    Security Misconfiguration → .env.example template, Vault for secrets
    Vulnerable Components   → Go modules + Python Poetry with pinned versions
    Auth/Session Mgmt       → Token rotation, device binding, short TTL
    Data Integrity          → SHA-256 hashes on SAR, blockchain immutability

15. KNOWN LIMITATIONS & FUTURE WORK
================================================================================

  ML LAYER:
    1. GNN production inference degrades to feature-only MLP (no message
       passing without pre-built subgraph from PostgreSQL edge table)
    2. 47 of 85 features are zero-padded in production (Bitcoin-specific
       Elliptic aggregated features with no banking equivalent)
    3. Ensemble weights derived from individual ROC-AUC only — no joint
       calibration has been performed
    4. Autoencoder scoring is inverted (Elliptic-specific) — AUC 70.9%
       makes it unsuitable as a primary classifier
    5. Federated learning stub exists but TensorFlow Federated was removed
       (Python 3.11 compatibility issue)
    6. Domain mismatch: Elliptic is Bitcoin; production transactions are
       bank wire transfers. Domain adaptation layer partially bridges this.

  BLOCKCHAIN LAYER:
    7. No Private Data Collections (PDC) — all 3 orgs see all fields;
       field-level regulator-only access is future work
    8. Single peer per organization — no HA peer redundancy
    9. Raft is CFT (crash fault tolerant), not BFT (Byzantine fault tolerant)
   10. No retry queue for failed blockchain receipts (fire-and-forget)
   11. GetComplianceReport does full ledger scan — slow at high volume

  SYSTEM LAYER:
   12. No federated identity (SSO/OAuth2) support in IAM Service
   13. Case Service SAR generation produces basic PDF — no regulatory
       template formatting (FinCEN/STR format)
   14. Alert escalation rules are time-based only — no ML-driven escalation
   15. Geographic risk scores are static — not updated in real-time from
       FATF/OFAC watchlists

  INFRASTRUCTURE:
   16. No multi-region deployment — single AWS region design
   17. Kafka replication factor of 1 in local dev (not HA)
   18. Blockchain network uses self-signed certs (cryptogen) — production
       requires a proper CA hierarchy
